# Samples

Complete working examples demonstrating Accordant features.

| Sample | Description |
|--------|-------------|
| [BankAccount](https://github.com/microsoft/accordant/tree/main/Samples/BankAccount) | Simple account with deposit/withdraw. Used in the [Overview](index.md). |
| [TodoList](https://github.com/microsoft/accordant/tree/main/Samples/TodoList) | Basic CRUD operations for todos. Used in [Your First Spec](tutorials/01-your-first-spec.md) tutorial. |
| [TodoList-Extended](https://github.com/microsoft/accordant/tree/main/Samples/TodoList-Extended) | Demonstrates response-dependent state (server timestamps) and server-generated IDs with request derivations. |
| [TodoList-FaultInjection](https://github.com/microsoft/accordant/tree/main/Samples/TodoList-FaultInjection) | Demonstrates indefinite failure handling with server-side and client-side fault injection. See [Indefinite Failures](how-to/indefinite-failures.md). |
| [Booking](https://github.com/microsoft/accordant/tree/main/Samples/Booking) | Demonstrates concurrency testing — the "double-booking" scenario where two customers try to book the same slot. |
| [JobQueue](https://github.com/microsoft/accordant/tree/main/Samples/JobQueue) | Demonstrates async operations with step functions, polling for completion, and server-generated result paths. |
| [DurableJobs](https://github.com/microsoft/accordant/tree/main/Samples/DurableJobs) | A complete contract/design/implementation case study: one atomic durable-job contract, checked safety and fair liveness, an implementation-shaped queue/lease/retry/crash design that directly refines it, a structurally mirrored thread-safe C# service, generated sequential and concurrent black-box conformance, and an explicit statement of the remaining implementation-to-design proof gap. |
| [WorkQueueRefinement](https://github.com/microsoft/accordant/tree/main/Samples/WorkQueueRefinement) | A leased work queue with competing workers, retries, cancellation and purging, refined against a client ledger. Combines `.Augment(...)`, `.WithWitness(...)`, `.Map(...)` and `.MapTransition(...)`, and contrasts weak and strong fairness. See [Checking Refinement](how-to/checking-refinement.md). |
| [WalRefinement](https://github.com/microsoft/accordant/tree/main/Samples/WalRefinement) | A write-ahead log with durable and volatile state, crashes, restart, recovery and replay, refined against an atomic key-value transaction that installs a whole per-key write set in one step. The commit-record flush is the linearization point, so the mapping is a plain `.Map(...)` over durable state; `.MapTransition(...)` declares which implementation actions the store hides, and which store action a crash performs when it dooms an in-flight transaction. Four deliberately broken implementations, a broken mapping, and a crash-loop fairness ladder. |
| [WalProcessCoroutines](https://github.com/microsoft/accordant/tree/main/Samples/WalProcessCoroutines) | **Experimental:** a write-ahead log written as *processes* — two concurrent one-shot clients (Alice/Bob) contending for a capacity-one request slot, and a server failure domain (a guarded request-handler launch, a page writer and a recovery worker) whose crash discards its continuations. The one slot serializes accepted transactions to match one redo record and one in-flight transaction — a bounded server/WAL model, not a single-writer KV-store assumption. The local handler reads as ordinary sequential code (append → flush → acknowledge) with no protective guards; a crash kills it and recovery — capturing its decision as a process local, with no recovery-only phase — reports in its place. A shared request/reply exchange survives crashes and carries one persistent reply per client. Adds an atomic guarded `StepWhen` resource claim and an enum-named `Step` to the coroutine runtime, and refines the guarded-action atomic store with the **state mapping alone** (no transition mapping is needed for either safety or the temporal fairness ladder — ≈0.9k nodes); an optional `.MapTransition(...)` demonstrates checked action declarations. A small property showcase adds stutter-safe **SafeRegex** episode-ordering properties, a **SafeRegex prefix + LTL/RLTL temporal suffix** (e.g. after `Submit·…·FlushCommit`, eventually `Committed`), and direct LTL invariants, with non-vacuity witnesses and a test that the safe lowering erases the graph's state-neutral control transitions. Not a supported API — see [Model-Checking Frontends](concepts/model-checking-frontends.md). |
| [OperationsModelChecking](https://github.com/microsoft/accordant/tree/main/Samples/OperationsModelChecking) | Compiles finite response-dependent `Operation` inputs to ordinary model-checking step functions, including `ENABLED`, fairness, and refinement. |
| [CoroutineModelChecking](https://github.com/microsoft/accordant/tree/main/Samples/CoroutineModelChecking) | **Experimental:** compiles finite replayable `async ModelTask` workflows to ordinary model-checking graph steps, and measures the replay-safety boundary the runtime can and cannot enforce. Not a supported API — see [Model-Checking Frontends](concepts/model-checking-frontends.md). |
| [OrderFulfillment](https://github.com/microsoft/accordant/tree/main/Samples/OrderFulfillment) | Model checks an implementation-shaped web application: a transactional checkout controller that commits domain state and outbox work together, and a payment worker that calls an external gateway whose answer may be ambiguous. Authors the same compiled model through all three frontends, contrasts weak and strong fairness, includes three deliberately broken variants, and pins where the experimental coroutine frontend stops. |

## Running a Sample

```bash
cd Samples/<SampleName>/<SampleName>.Tests
dotnet test
```

Most samples include both an API project and a Tests project. The tests demonstrate the Accordant spec and can be run directly.
